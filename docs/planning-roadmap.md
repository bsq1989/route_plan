# 目标消除规划与分阶段验证计划

本项目面向可运行、可复现的落地 demo。小车通过前置消除区清除目标点，首要目标是在现有运动和安全规则下完成全部目标消除。路程、耗时和转向次数属于后续优化项，不作为首版必须达到的最优性要求。

开发顺序为：静态完整观测 → 车头方向加点 → 随机加点。每个阶段通过验收后，再进入下一阶段。当前只启动第一阶段。

## 问题定义

这是任务规划与路径规划的联合问题。

- 任务规划决定先处理哪些目标、从哪个方向接近，以及是否一次消除多个目标。
- 路径规划决定如何安全转向、前进、绕行并到达所需位姿。
- 某条接近路径不可行时，需要尝试其他方向、中间位置或目标顺序。

目标点在消除前也是车身安全轮廓不能触碰的障碍，消除后不再参与后续碰撞。因此，路径可行性随消除状态变化，不能只用一张固定的点间距离表表达全部问题。

规划状态至少包含 `(x, y, yaw, remaining_target_ids)`。同一位姿下，剩余目标集合不同，后续可行动作也可能不同。

## 当前基础与技术路线

已有仿真提供 `Scene` 几何规则、`PoseController` 目标位姿执行器、手动界面和无窗口调用。自动任务规划、自动避障与 OMPL 适配尚未实现。

首版采用带回溯的启发式搜索，参考 PythonRobotics 的搜索实现；需要复杂接近路径时，引入 OMPL 辅助运动规划。两者都必须遵守本项目的运动模型和连续碰撞、消除规则。

| 组成 | 职责 |
| --- | --- |
| 任务搜索 | 生成候选接近方式、选择分支、记录剩余目标、遇到死路回溯 |
| 运动规划 | 先尝试简单的转向和直线组合，必要时通过 OMPL 搜索中间位姿 |
| 仿真规则与执行 | 检查整段运动，处理消除和碰撞，执行并回放计划 |
| 验证工具 | 固定场景、批量运行、记录结果、复现失败 |

算法代码独立于 `sim/` 放置，不混入 `app.py` 显示层。具体模块和接口在第一阶段实现时确定；本计划不代表已有对应代码。

参考入口：

- [OMPL 状态与运动有效性检查](https://ompl.kavrakilab.org/core/stateValidation.html)

## 第一阶段 静态完整准确观测

### 输入假设与完成条件

第一阶段从最简单的观测条件开始：**任务启动时，所有目标均已被完整、准确地观测到。** 规划器知道每个目标的位置与标识，执行期间不会新增目标，也不会发生位置修正、漏检补充或外部删除。目标集合只会因合法消除而减少。

地图边界、车辆尺寸和初始位姿已知，使用现有仿真的确定性模型。车辆参数读取 `sim/config/robot.yaml`，不在规划器中另设默认车型。消除器安装位置、位姿参考点和旋转中心继续采用现有配置约定；这些仍是仿真假设，不能作为实车测量结论。

本阶段不引入传感器视野、观测噪声、延迟发现、运行中加点、自主巡游、ROS 或 Nav2。

成功条件为：计划在仿真中完整执行后，剩余目标数为零，且没有碰撞、越界或非法运动。不要求回到起点，不额外约束最终位置和朝向。

### 必须遵守的约束

几何与接口细节以仓库 [AGENTS.md](../AGENTS.md) 和 [仿真说明](../sim/README.md) 为准，规划器重点保持以下约束：

1. 位姿使用 map 坐标系，Python API 的 yaw 使用弧度。
2. 每条目标位姿指令的位置必须位于当前车头前半平面，正侧方允许；同位置可只调整朝向。
3. 运动为原地转向、向前直线、末端原地转向，禁止倒车和边走边转。
4. 消除区在前进和旋转中都有效，可以同时消除多个目标。
5. 车身外扩后的安全轮廓不能触碰剩余目标；安全轮廓和消除区都不能触碰地图边界。
6. 检查整个运动过程。先消除的点不再触发后续碰撞；同一点同时接触安全轮廓与消除区时，碰撞优先。
7. 碰撞后按现有规则冻结，不以重置场景的方式继续同一次任务。

### 规划流程

1. **读取初始状态。** 保存地图、完整车辆参数、初始位姿和全部目标，作为规划和复现的共同输入。
2. **生成候选接近方式。** 围绕目标采样若干方向和车辆位姿，使目标进入前置消除区。目标坐标不是必须到达的车身中心坐标，不能直接把车开到目标点上。
3. **尝试简单运动。** 优先生成符合控制器约束的目标位姿序列。保留只转向、暂时不消除目标的移动，以及必要的中间位置调整。
4. **模拟候选动作。** 在独立状态副本上调用相同的几何规则，获取动作结束位姿、实际消除集合和失败原因。动作途中消除的所有点都要更新，不限于候选动作原本瞄准的目标。
5. **搜索与回溯。** 优先探索有望取得进展的分支，保留其他候选。某个分支失败后，从此前的规划状态换方案，直到找到全部消除的计划或达到搜索预算。
6. **补充绕行能力。** 当简单接近动作不足时，通过 OMPL 搜索中间位姿，并将结果接回任务搜索。
7. **完整回放。** 将候选完整计划从相同初始状态重新交给仿真执行，只有回放满足成功条件，才报告成功。

搜索优先级可以参考本次消除数量、接近距离和转向代价，但这些仅用于安排探索顺序。不能只保留眼前消除最多或距离最近的一条分支，也不能要求每一步都必须消除目标。

回溯发生在规划状态中，不代表让真实车辆倒退。首版静态 demo 先规划出完整方案、回放验证，再用于窗口演示。

### OMPL 适配边界

OMPL 在第一阶段内分步接入：先跑通简单动作与任务搜索，再补充绕行能力。阶段验收至少包含一个由 OMPL 生成运动方案、并完整回放通过的固定绕行场景，不以“已安装库”作为完成标志。

适配器必须显式表达原地转向与直线前进；不能直接执行通用位姿插值生成的边走边转轨迹。每个运动段都要验证旋转扫掠、前进扫掠及其间的目标消除事件。

一段路径如果中途消除了目标，后续段必须基于更新后的剩余集合检查。不得只按路径终点更新消除状态，也不得仅按二维栅格或车身中心判断安全。具体采用的 OMPL 状态与传播方式在实现适配器时确定，并用固定场景验证。

### 实现顺序

| 步骤 | 交付内容 | 完成依据 |
| --- | --- | --- |
| 1 | 场景输入、独立试算状态、动作结果与回放入口 | 试算不修改实际场景，试算与回放的几何结果一致 |
| 2 | 单目标与少量目标的接近候选生成 | 能处理不同方向，拒绝碰撞动作，更新实际消除集合 |
| 3 | 带回溯的任务搜索和完整计划输出 | 能换接近方向、换消除顺序，并使用暂不消除目标的中间动作 |
| 4 | OMPL 运动适配与绕行场景 | 输出能被现有执行器合法执行，完整回放通过 |
| 5 | 静态回归集、随机批量验证和窗口演示 | 固定回归通过，批量结果和失败场景可复现 |

若需要新增仿真状态复制或恢复接口，应显式实现并验证；当前 `scene.snapshot()` 用于状态导出，不假定已有完整恢复能力。

### 验证场景与验收

先建立有已验证可行轨迹的固定场景，再扩大规模。场景标签描述实际验证的能力，不能仅凭点位外观断言必须采用某种顺序。

| 场景 | 重点检查 |
| --- | --- |
| 空目标 | 直接成功，不产生无意义运动 |
| 单点位于前方、侧方、后方 | 合法调整朝向与接近方式；后方点不能直接下发为位置目标 |
| 少量分散点 | 连续消除和剩余集合更新 |
| 多点落入同一消除动作 | 一次消除多个点，避免重复处理 |
| 直接接近碰撞，换方向可行 | 接近方向搜索 |
| 某个顺序失败，另一顺序可行 | 任务分支回溯 |
| 需要中间位置或绕行 | 非消除动作及运动规划 |
| 首尾安全但旋转中途碰点 | 连续运动验证与碰撞优先规则 |
| 目标靠近边界或点群密集 | 安全轮廓与消除区共同约束 |
| 固定种子的随机场景 | 扩大覆盖，保存成功、超时和未找到解的情况 |

人工确认可解的固定回归集应全部完成，并且每条成功计划完整回放无碰撞、无越界。增加场景难度时先验证基准轨迹，避免把实际不可解场景误作为必过项。

建立首批回归集时，将必过场景、基准轨迹、每个场景的搜索预算和规划器配置纳入版本管理。验收使用冻结的场景与配置；新增场景单独扩展，不能通过移除失败用例或临时放宽预算使既有验收通过。

随机场景不保证可解，不要求所有随机种子都成功；需逐个记录预算和结果，分析失败原因。有限采样、离散化或时间预算下未找到解，不能直接报告原始连续问题无解。

每次运行至少记录：

- 地图、初始位姿、完整车辆参数、目标 ID 与坐标。
- 规划器配置、候选采样参数、随机种子和搜索预算。
- 计划动作、回放后的剩余与已消除目标、失败发生的动作与原因。
- 结果状态：成功、输入非法、预算耗尽、候选搜索结束但未找到解，或回放失败。
- 规划耗时、展开状态数、消除数量；路程和转向量作为观察指标。

回放失败属于规划或适配缺陷，不能记作成功。生成记录和截图放入被 Git 忽略的 `sim/output/`；可维护的测试场景与回归断言纳入版本管理。

修改几何、控制或配置逻辑后，执行现有单元测试：

```bash
uv run --project sim python -m unittest discover -s sim/tests -v
```

新增算法测试与上述测试共同构成回归检查；若修改界面，还需导出截图检查中文字体、控件及几何轮廓。算法命令和自动演示入口在实现后补充，不在本计划中假定它们已经存在。

## 第二阶段 车头方向加点

第一阶段验收通过后，在任务执行期间加入目标。新增点位于小车当前朝向的前半平面，并满足现有添加规则，包括不落入当前安全轮廓及其边界。

先使用可复现的手动或定时事件，不引入观测噪声。分别验证远离当前路径、影响即将执行的动作，以及一次新增两三个点的情况。

系统需要接收目标更新，检查当前动作和剩余计划；计划仍有效时继续，受影响时停止旧指令并重新规划。新点不在当前碰撞区，不代表下一段运动一定安全。

本阶段增加观测版本和旧计划失效检查，避免用过期目标集合继续执行。具体更新频率、停止与重规划时机在静态能力稳定后实现。

验收要求：静态回归继续通过；在约定可解场景中正确处理加点事件、保持安全；停止加点后完成剩余目标消除。

靠近以后才发现额外目标的模拟，在上述加点能力通过后补充。届时区分真实点位与规划器可见点位，碰撞仍按真实点位判断，并显式配置发现距离和更新延迟。当前仿真没有惯性与刹车距离，仿真通过不代表已验证实车制动能力。

## 第三阶段 随机加点与持续运行

第二阶段验收通过后，放开新增方向，在地图允许区域随机加点，仍遵守添加规则。使用固定种子和可记录的加入时刻，覆盖侧后方新增、连续新增、任务清空后再次新增等情况。

重点检查目标是否遗漏、计划是否反复震荡、长时间运行是否卡住，以及早加入的目标是否长期得不到处理。根据实际失败案例增加等待时间优先级等调度策略。

在约定可解场景中持续安全运行，停止加入后完成剩余目标，是本阶段验收目标。任意随机加点可能产生不可解场景，需保存复现，不能承诺所有随机输入都能全部消除。

当前目标清空后进入等待状态。没有目标时主动巡游、如何选择探索区域，以及真实观测误差下的位置关联与修正，属于后续另行定义的能力。

## 当前开发边界

下一步只实施第一阶段：完整准确观测、静态目标、任务与路径联合求解、完整回放验收。第二阶段和第三阶段保留为后续路线，不提前引入在线观测与长期调度的复杂度。
