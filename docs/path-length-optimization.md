# 路径长度优化与 A/B 验证

> 以下 benchmark 是历史点模型及当时车型参数的结果。当前新场景已改为直径 10 cm 的圆形目标，消除区已修正为宽 35 cm、深 24 cm；历史统计不代表新几何模型的成功率。旧记录按原始点模型恢复。

在静态完整准确观测阶段，增加路径长度优化方法 `LengthPlanner`。硬约束仍是全部清除、禁止倒车、遵守连续碰撞与地图边界规则；优化目标是车身中心的总平移距离，不对原地转向次数或耗时加权。最终位置与朝向自由，也不要求返回起点。

当前定位为有限时间内改善可行路线的工程方法，不要求或宣称全局最优。原有 `StaticPlanner` 保留为可行性 baseline。

## 优化过程

1. 先取得并验证一条完整可行路线，作为始终保留的初解。
2. 尝试用更短的安全连接替换中间路径，并检查后续动作。跳过某次消除后，原本安全的后续路径可能碰到尚未清除的点，因此不能只检查替换段的首尾。
3. 从仿真实际消除事件提取目标顺序，局部反转一段顺序，再重新选择接近方向和车辆位姿。试算时保留其他未清除点作为障碍；一次动作消除多个目标时，后续直接跳过已经清除的目标。
4. 利用剩余预算进行有限宽度的候选搜索，按累计平移距离及剩余距离估计排序，保留若干可行分支。
5. 每次只有完整清除、全程安全且实际路程更短时，才替换当前方案。最终再以 0.04 秒步长独立回放；改进方案验证失败时保留原可行方案。

候选搜索的距离估计使用包围消除区的圆形区域，忽略方向与障碍，计算区域间最小生成树距离下界。该下界只辅助搜索排序和剪枝；有限方向采样、束宽、局部顺序调整与预算限制仍会漏掉其他更短解。

任务规划和运动规划接口保持可替换。优化阶段仍使用相同的运动连接器与仿真规则；OMPL 的绕行能力及保守目标状态处理方式沿用静态 baseline。

## 使用方式

在仓库根目录激活 `route-plan` Conda 环境后：

```bash
# A：原有可行性方法，找到首个完整方案即停止
route-plan solve --method feasibility --scenario random --seed 7 --timeout 3

# B：在可行性初解上继续优化距离，并打开自动执行窗口
route-plan solve --method length --scenario random --seed 7 --timeout 3 --show

# 同一初始场景、同一可行性初解的配对比较
route-plan compare --seeds 0:100 --timeout 3 --output sim/output/length-ab

# 直接回放保存的 B 方案，不重新搜索
route-plan replay sim/output/length-ab/B-random-7.json --show
```

使用 uv 时，在上述命令前加 `uv run --project planner`。Python API 同样支持独立调用 `LengthPlanner(options).plan(scene)`，或通过 `initial=a` 复用已验证的 A 方案。

## 对比设计

采用配对场景测试：默认前方点群、默认四周包围，以及随机种子 0–99。每个随机场景固定 40 个目标。A、B 使用相同地图、初始位姿、完整车辆参数、目标集合和碰撞规则。

A 使用 `StaticPlanner`，取得首个可行方案后停止。B 复用该次 A 的实际方案，避免两次随机求解得到不同初解而混淆优化效果。每场搜索预算 3 秒，A 的初解耗时计入 B 的预算，B 利用剩余时间优化。最终完整回放可能额外增加墙钟耗时，记录中的 `elapsed` 包含验证开销。

首先比较全部清除率和回放安全，再比较两组均成功场景的路径长度。失败或少清除目标产生的短路线不计作改善。路径降幅按两组成功配对的总距离计算，同时记录改善、不变及变长的场景数量。

当前预算耗尽时，只要已有完整可行方案，结果仍为 `success`；`optimization.termination` 记录优化结束原因，`optimization.baseline_length`、`saved_length`、`saved_fraction` 记录相对于初解的变化。时间与连接试算预算由初解和优化阶段共享；不同阶段的试算计数分别保存在优化元数据中。

完整 A、B 输入与动作记录保存在被 Git 忽略的 `sim/output/length-ab/`，可通过 `replay` 单独检查。版本化验证摘要保存在 [`length-ab-v1.json`](../planner/benchmarks/length-ab-v1.json)。

## 2026 年 11 月 8 日实测结果

本机 Conda `route-plan` 环境执行上述完整批次，共 102 个场景，两组均逐条独立回放验证。默认车辆参数与输入范围保存在验证摘要中。

| 指标 | A 可行性 baseline | B 路径长度优化 |
| --- | --- | --- |
| 完整清除且无碰撞 | 102/102 | 102/102 |
| 累计平移路程 | 4632.97 米 | 3962.25 米 |
| 相对 A 的总路程降幅 | — | 14.5% |
| 平均规划及验证耗时 | 0.32 秒 | 3.24 秒 |

102 组中，101 组路程缩短，1 组不变，0 组变长。不变的是随机种子 90，优化器保留其可行初解；不表示该路线已被证明最优。单场景路程降幅中位数为 13.4%。

| 示例 | A 路程 | B 路程 | 缩短 |
| --- | --- | --- | --- |
| 前方点群，10 个目标 | 6.14 米 | 5.79 米 | 5.7% |
| 四周包围，32 个目标 | 16.72 米 | 15.85 米 | 5.2% |
| 随机种子 7，40 个目标 | 41.12 米 | 35.96 米 | 12.6% |
| 随机种子 28，40 个目标 | 49.70 米 | 45.32 米 | 8.8% |
| 随机种子 42，40 个目标 | 43.61 米 | 38.57 米 | 11.6% |

规划器 21 项测试通过，覆盖更短路线的完整清除、不同步长回放、预算耗尽保底、最终验证失败回退、零平移转向代价，以及 CLI 的同输入配对记录。

本次结果说明长度优化在该固定测试集上有效，代价是更多规划计算时间。运行时间限制、OMPL 随机流和机器负载会影响改进幅度；保存的完整计划可独立回放，复测不保证重新搜索得到完全相同的路线或耗时。当前仍处于静态完整准确观测阶段。
